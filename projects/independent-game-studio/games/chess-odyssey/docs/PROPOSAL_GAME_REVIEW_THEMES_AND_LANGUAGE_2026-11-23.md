## Owner review — additional comments and accepted design direction (2026-11-23)

**Status:** product-design direction accepted for discussion; **NO implementation authorization given yet**. Record the clarified requirements before asking for explicit permission to implement. This supersedes conflicting presentational assumptions in the initial proposal, not the existing B9 security gates.

1. **Visual direction accepted:** the dark navy/royal-gold presentation of the concept image was liked. Preserve the coherent premium visual direction without treating the mockup as an exact pixel-perfect or English-only specification; UI must support RU/EN/AZ.
2. **Compact on-demand selectors, not permanent panels:** "Board theme" and "Piece set" are **separate collapsed dropdown/accordion controls** (both closed by default). Click first to reveal a thumbnail grid of 10 options; click chosen thumbnail to apply; click header again or elsewhere / Escape to collapse. Selected name + miniature swatch remains visible when collapsed. The same behavior applies independently to piece styles. Do **not** leave 20 images occupying the normal game screen. Preview images (small PNG or equivalent) display only when the corresponding control is expanded; screen-reader labels/keyboard access and selected state required.
3. **Board-only immersive mode:** add **Fullscreen / Wide board view** as a user-selectable control. On desktop, immersive screen uses **about 50% of viewport width for the chessboard**, and the other half for move history, clocks, action buttons and (where permitted) analysis; avoid stretching the board to fill the entire monitor. Preserve square proportions and margins. On narrow phones, stack the square board above controls rather than forcing a microscopic 50%-width board. Fullscreen API where supported, escape with Escape or visible Exit, safe fallback to maximized panel; entering/exiting never alters a game/clock/settings.
4. **Training arrows are an actual required feature:** in **coached learning / teaching mode**, show an arrow on the board from a legal origin square to a suggested destination and (where applicable) distinguish candidate vs strongest recommended move. Provide understandable one- or two-line explanation and alternative. During quiz/guess-the-master lessons avoid unintentionally revealing the answer before learner has attempted it; use a clearly presented "Show hint / Best move" control or appropriate stage gate for those exercises. In free coached practice, arrows may be shown immediately/continuously as training feedback if activated. Arrows update with the current position, disappear or refresh after the move, and never block mouse/touch/keyboard square interaction.
5. **Finished-match review arrows + every-ply labels:** in **postgame** review, choosing any half-move highlights actual played origin→destination and shows a contrasting best-move / alternative arrow from the position **before** that move. Each side's actual played move receives a classification badge and a short explanation. The user can step backward and forward, inspect projected continuations and a per-side game report. Arrows/analysis MUST NOT leak into live competitive independent AI or PvP matches.
6. **"Brilliant" is VERY GOOD, never ironic:** `Brilliant / Блестящий / Parlaq` means an **exceptional, creative or difficult strong move**, not a sarcastic "bad" move. Use positive celebration styling (e.g. `!!`, distinct cyan/gold), not a red error symbol. Any footnote/asterisk in the prior illustration merely meant **this special label needs its own validated criteria**; it must NOT imply poor quality. If not provable, omit the label and classify under objectively supported categories.
7. **Localized, collapsed move-grade legend:** add a clickable `What do move symbols mean? / Что означают оценки? / Gediş qiymətləndirmələri nə deməkdir?` help header. It is **collapsed by default**, expands to explain all supported labels, icon notation, example and category meaning in the *currently selected* RU/EN/AZ language, and closes again. The small move badges themselves should have accessible short tooltip/description; use text as well as colors. The legend must include distinctions for `Brilliant (!!)`, `Best (★)`, `Excellent (!)`, `Good (✓)`, `Ordinary (—)`, `Inaccuracy (?!), Mistake (?), Blunder (??)`, and optional Book/Not Evaluated. Do not list `Dangerous` as a numeric quality class unless a robust separate tactical-risk signal exists; it can be an explanatory warning label instead.
8. **Acceptance of teaching/review direction:** the owner agrees with move-by-move instructional feedback and **complete analysis after ordinary AI and finished human PvP**. Genuine engine-backed numerical accuracy/white-vs-black breakdown still needs implementation and validation, not arbitrary sample scores.

**Interaction contract:** only settings that are **opened by the user** reveal their options; optional detail panes can be closed to return to a clean chessboard. Save selected board/piece preferences and open/closed UX state only where helpful; persist game state and score separately. No changes to code/assets/Neon/production are authorized by this review comment alone.

Therefore **never advertise deep Stockfish analysis inside a lone `.html` unless a new offline-safe worker-bundle is actually engineered and QA-passed**. ## Scope proposal — ordered priorities

### P0. Unify languages and move navigation, fix discoverability
1. Persistent **global RU | EN | AZ** selector in the visible top application bar, on mobile and desktop. Switching language **must not start/reset a game**. Propagate to all tabs: Practice, Academy, Masters, Progress, clocks, modal dialogs, review, accessibility strings, status messages and all new settings. Keep only one language source of truth, with backwards-compatible migration from existing separate locale settings.
2. Move browser toolbar on any ordinary game's board: `|◀` beginning, `◀` previous half-move, `▶` next half-move, `▶|` latest/live; click a SAN in the move list to jump to it, show `ply / total plies`. On completion, allow all 0…N positions, including initial FEN, captures, castling, promotion and checks. Provide **Return to live** when match is still running.
3. **Separate concepts:** `Review previous position` is a non-destructive *read-only timeline cursor*; `Undo last move` changes the actual practice game (and may invalidate AI scoring or require clock/history rollback). Never use the same control for both. During independent/competitive AI and online PvP, historical browsing is allowed while the real authoritative game continues, but actual move undo is restricted/disabled by game policy. No hints/engine evaluation shown for active competitive PvP.
4. Keep move-timeline cursor independent from canonical `game` and clock, with explicit return to live; UI board reconstruction from immutable SAN/PGN via chess.js. Handle reload, keyboard focus (existing arrows navigate squares when the chessboard has focus), timestamps and last move highlighting. Avoid phantom changes to score, localStorage and server state.
5. Add visible version in standalone header and one concise filename/hash support aid. E2E compare separately `index.html`, freshly generated `v0.8.0` standalone, ZIP/localhost; verify screenshot/colleague's exact copy when available. Do not ask for rework of existing legacy content without a demonstrated gap.

### P2. Complete two-side per-move Game Review
**Two analysis states, never mixed:**
- `Learn / coached practice`: after the learner plays a legal move, show short on-board move verdict plus optional explanation, tactical threat and alternative; optionally richer Stockfish assessment when a real licensed analysis Worker is available. Give actual immediate feedback during Academy only when appropriate for a pedagogical exercise; never spoil the next expected answer before user commits. Avoid claiming current shallow COACH heuristic is an objective engine score.
- `Completed ordinary AI / PvP / independent match`: compute a **full post-game asynchronous** evaluation, scoring **every half-move** for both colors from canonical played PGN. Each classification must map to a specific move, FEN, evaluated before/after position, engine depth, engine version, best legal alternative, PV and uncertainty/fallback. The analysis is separate from the server-authoritative game, clocks, results and AI Ladder Index.
- `Active PvP or unassisted competitive AI`: **no live Stockfish evaluation, hint overlays or best-move reveal**. Analysis is available only after the server commits a finished result, for both players.

Implement distinct **visual badges**, not just emoji, and a textual accessible label for each; put a single **expandable/collapsible trilingual move-label legend** behind a `?`/`Meaning of symbols` control (closed by default) and show a small contextual hint on each badge; retain chess annotation marks `!`, `?`, `?!`, `??` where meaningful. The full per-move classification is a **new deterministic documented methodology**, preferably based on calibrated, versioned **win-probability / expected-points loss**, rather than arbitrary raw centipawn cutoffs. The two prominent references are *Chess.com Game Review* classifications (published 9 Feb 2026 Expected Points V2, including special-case Brilliant/Great/Miss) and *Lichess Accuracy* (Win% and volatility-weighted metrics). **Reference these ideas, do not misrepresent our scoring as the same proprietary Chess.com algorithm.**

**Evaluation architecture:** existing `engine-bridge.js` currently parses only `bestmove` for play, not `info ... score cp|mate, multipv, pv, depth`. Build a *separate* `AnalysisBridge` with UCI `MultiPV` support and score normalization from side-to-move into consistent player/white point of view. Analyze initial and each intermediate legal game position, including mate and special draw score; use caching by `PGN/FEN, ply, engine SHA/version, depth, perspective and method version`. Collect exact completed/failed/countable moves and avoid mixing only-available scores with unanalysed moves. Provide user-configured CPU/time budget (quick/balanced/deep); do not block board, UI or game clock, and do not queue one long job per render. Expose partial progress and cancellation. Reconcile exact PGN replay and protect against worker timeout/fallback. Genuine engine is available in ZIP via localhost/HTTPS; unsupported `file://` mode displays unavailable/limited verdict, never fictional deep scores.

**Full report format:** `White vs Black` columns with independently computed accuracy (%) and counts for Best, Excellent, Good, Inaccuracy, Mistake, Blunder, Book/Unclassified; total analyzed plies for each color, explicit denominator/exclusions, evaluation chart over each *half-move*, opening/tactics/coordination/conversion/endgame **coaching dimensions only when measurable by published transparent heuristics**. Treat phase categories as optional educational annotations, **not pseudo-authoritative 5/10 grades without source**. Differentiate **ply (half-move)** from **full turn** and actual stored result from checkmate claim. Avoid claims like engine-estimated FIDE Elo or guaranteed real skill rating.

**Review UX and training arrows:**
- Step navigation buttons `first/prev/next/last`, clickable timestamped SAN list and `next critical mistake`; reconstruct board as of selected ply, highlight the actually played move with one arrow and the objectively recommended alternative with a visually distinct arrow (only after the move/when fair-play policy permits), plus an accessible category badge. At each move show `Actual: ... / Best: ... / Position before -> after / Why / one or two likely continuations`; explain in simple RU, EN or AZ. Never reveal an evaluation during active competitive play.
- Progress graph anchored to actual plies. Click a graph point to jump to that position.
- `Retry from this position` is a **separate training fork**, never a modification of finished PGN/official result or PvP cloud record.
- Training uses board arrows to show legal directions and the recommended best move when hints/teaching feedback is permitted, with short explanations; dedicated guess-the-move quizzes guard against spoiling answers before an attempt. On mobile, board occupies the upper panel and report collapses below; clock is only live during active game. Saving analysis is optional and bounded.
- In a user-requested immersive **Fullscreen / Wide board view**, the board occupies roughly half a desktop viewport (not 100% width); useful game data and the move/analysis panel occupy the rest, while phones stack vertically. Settings and move-classification legend remain collapsed by default.
