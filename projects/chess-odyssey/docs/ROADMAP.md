## Owner-approved v1.0 expansion — 2026-11-21: timed play AND live friends PvP

**Core product decision (supersedes earlier postponement of human-vs-human):** Chess Odyssey is a learn → train against AI → play against other humans → study game progression. Human-vs-human real-time play with friends **is required for first v1.0**, not a vague future add-on. Early launch targets approximately **5–10 invited friends/colleagues**, not a mass public chess platform. Existing B0–B7 code and QA #339 (238/238 PASS) are a protected verified development baseline, not evidence for new B8–B10.

### B9 proposed architecture (DESIGN ONLY, not deployed)
- **Frontend:** existing playable HTML/CSS/JS remains online via an HTTPS static/web host (provider and domain to be chosen); retain single-file offline HTML for AI/Academy/history with clearly unavailable PvP/cloud features. HTML is still used by online websites; a frontend rewrite is not necessary solely to become online.
- **AI and rules:** local chess.js and licensed Stockfish 19 Lite Worker/WASM remain in browsers for private AI training and analysis; disable AI move suggestions during a fair PvP match. Never trust client move legality, outcome, clocks or participant roles.
- **Preferred backend: Neon**, subject to concrete feature/security evaluation: Postgres for users, game sessions/moves, persistent progress, invites and ratings; Managed Better Auth for user authentication; Functions for authoritative authenticated move submission and game-state transitions; optional Data API for per-user data with database RLS. Do not put database secrets in frontend.
- **Live updates:** Neon Realtime is in public beta (as of 2026-11-21) and specifically does NOT yet provide row-level security for live queries; NEVER expose private game records via unrestricted frontend live subscriptions. Evaluate a secure per-game authorized server-side WebSocket gateway (Neon Functions where verified suitable), private subscription design, or short interval polling fallback for 5–10 users. Prove authorization and live consistency with two real accounts before release. No assumption that Neon Realtime alone is a secure multiplayer referee.
- **Game authority:** server-side transactional check of auth, membership, turn, legal chess.js state, monotonic move number/optimistic version, committed canonical FEN/PGN, atomic clock debit/increment based on trusted server time, expiry and rules including material limits, replay/idempotency, illegal or racing requests. One decisive game outcome; client animation is display only. Never rely on JavaScript timer in a browser tab as the arbiter.
- **Data migration:** existing localStorage (B0–B7 player progress / 31 games / achievements) preserved; implement account-linked opt-in import with stable IDs, dedupe, revision reconciliation and backup/restore; no destructive overwrite on first sign-in. PvP results separated from uncalibrated AI Ladder Index, no fabricated universal Elo.
- **Cost and scope:** capacity is aimed at 5–10 invited users; Neon free tier looks viable but region, feature availability, monthly quotas and any usage charges must be verified live before implementation. Hosting frontend remains a separate deployment concern for both Neon and Supabase, but a dedicated always-running chess-engine server is NOT required.

### Acceptance and implementation checkpoints
1. PRECHECK: old source, saved state contracts, tool/library licenses, current CI and up-to-date Neon capabilities. Keep B0–B7 untouched as historical evidence.
2. Implement + test B8 clock truth first, independently of artistic sandglass and sounds. Verify Bullet/Blitz/Rapid and unlimited; both colors; refresh, tab suspension, promotion, AI thinking, pause policy, timeout/material exception and fair-match no-help isolation.
3. Implement online identity / persistent data in a non-production test environment; validate private data separation and lossless migration from existing local save.
4. Implement B9 server-authoritative multiplayer invites/room, commit protocol, live propagation or justified fallback, rematch, reconnection and termination; test two distinct browser sessions/users under slow network, concurrency, unauthorized requests and reload.
5. Finish B8 UX, bounded extra openings, real postgame analysis, RU/EN/AZ parity, accessibility. Preserve offline HTML with explicit online-only feature markers.
6. Finish historical independent archival reconciliation and B0–B9 full regression; actual owner desktop/mobile UAT; document exact QA PASS/FAIL/BLOCKED, CI IDs and rollback artifact.
7. Owner separately chooses domain/host and explicitly authorizes production release; deploy only after accepted gates and re-test the live site.

**Status boundary:** This roadmap commit is documentation-only. No Neon project, user accounts, code, schema, database writes, web host, multiplayer sessions, main merge or deploy have been created by this decision.
